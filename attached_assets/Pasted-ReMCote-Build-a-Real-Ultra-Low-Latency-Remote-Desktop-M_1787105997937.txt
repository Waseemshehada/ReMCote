ReMCote — Build a Real Ultra-Low-Latency Remote Desktop MVP

You are building a real working product called ReMCote.

ReMCote is a high-performance remote desktop platform inspired by the simplicity of Chrome Remote Desktop, but engineered from the beginning for extremely responsive professional video-editing workflows.

This is NOT a UI mockup.

This is NOT a simulated remote desktop.

This is NOT screenshot polling.

This is NOT a VNC wrapper.

This is NOT a normal web screen-sharing application.

The goal of this first version is very specific:

Install a lightweight Windows Host application on Computer A, open the ReMCote website on Computer B, enter the Device ID, connect, and obtain a real interactive live desktop stream with extremely low latency, smooth mouse/keyboard input, high frame rate, and high image quality.

The first version must prioritize proving the streaming architecture.

Do not overbuild account systems, billing, organization management, file transfer, chat, recording, admin panels, or other unrelated features.

Build the smallest architecture capable of proving that ReMCote can feel exceptionally responsive.

1. NON-NEGOTIABLE ENGINEERING PRINCIPLE

Architecture:

The Replit server is the control plane.

Video must travel peer-to-peer whenever networking permits it.

Use the Windows:

with:

* Direct3D 11
* IDXGIOutputDuplication
* AcquireNextFrame
* GPU textures

Capture the primary monitor only for MVP.

Do NOT copy every frame to CPU memory.

The preferred pipeline is:

Windows Desktop
      ↓
DXGI Desktop Duplication
      ↓
D3D11 GPU Texture
      ↓
GPU Color Conversion if required
      ↓
NVENC
      ↓
WebRTC

Design for zero-copy or minimum-copy GPU processing.

Avoid:

GPU
↓
RAM
↓
CPU conversion
↓
GPU

unless absolutely unavoidable.

Every unnecessary memory copy is considered a performance defect.

9. FRAME QUEUE PHILOSOPHY

Remote desktop responsiveness matters more than displaying stale frames.

Do NOT build a long frame queue.

If encoding/networking cannot keep up:

drop old frames instead of increasing latency.

Maximum desired pending video queue:

1 frame

Conceptually:

Newest frame wins.

A remote desktop that displays every frame 300 ms late is worse than one that drops frames but remains current.

Optimize for freshness.

11. NVENC LOW-LATENCY CONFIGURATION

The encoder must be optimized for interactive remote desktop use, NOT offline video quality.

Use NVIDIA’s ultra-low-latency / low-latency tuning.

Prioritize:

* extremely short encode time
* minimal buffering
* immediate frame output

Avoid settings that require future frames.

For the low-latency profile:

* no B-frames
* disable lookahead
* minimize internal buffering
* low-latency/ultra-low-latency tuning
* fast NVENC preset appropriate for interactive streaming
* frequent recovery/keyframes without excessive bandwidth
* adaptive bitrate
* low-delay behavior

Do not blindly maximize compression efficiency if it increases latency.

Latency wins.

15. MOUSE LATENCY: SPECIAL OPTIMIZATION

Mouse response is one of ReMCote’s most important features.

Create a dedicated WebRTC DataChannel:

input-pointer

Configure it for low latency.

Pointer movement packets should prefer freshness over guaranteed retransmission.

Use:

ordered: false
maxRetransmits: 0

for high-frequency mouse movement.

If an old mouse movement packet is lost, DO NOT retransmit it.

The next movement is already more useful.

Mouse buttons/wheel may use appropriate reliable behavior where required.

⸻

16. CLIENT-SIDE CURSOR

Implement a local client-side cursor overlay.

When the user moves the mouse inside the remote desktop:

1. update the visible cursor position locally immediately,
2. send the mouse movement to Host,
3. Host injects the movement into Windows.

Do not wait for the remote video frame before showing the cursor movement.

This is designed to produce near-instant perceived pointer response.

The remote system state remains authoritative.

The cursor overlay is only a latency-perception optimization.

39. NATIVE WEBRTC

Use a production-capable native WebRTC implementation.

The Host must behave as a real WebRTC peer.
